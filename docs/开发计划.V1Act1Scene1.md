# JoshiTeich V1 Act1 Scene1 开发计划

日期：2026-10-14

本文件只规划 `Act1Scene1`：从真实 Scene1 数据到 Joshi 版本 Corollary 3.12。
Scene2、`abc`、strong `abc`、Vojta 和 Act2 不在本文件的完成范围内。
所有证明项禁止 `sorry`、自定义 `axiom`、`admit` 和隐藏 `opaque` 证明。

## 0. 动态边界审计契约

### 0.1 目的和基线

在 Corollary 3.12 的精确形式尚未写入 Lean 之前，不能把 Prologue 的当前边界当成
最终的数学假设集。P0.17 建立的边界记为 `Prologue-R0`：它是一个可复核的基础设施
基线，不是对未来 3.12 需求的永久承诺。任何把声明加入 Prologue、从 Prologue 移出，
或在两者之间拆分的行为都必须产生一个新的边界修订记录，不能通过直接编辑旧结论
来改变信任边界。

截至 S1.115，当前边界版本为 `Prologue-R5`。S1.112 将 Tate/q 参数的 Prologue 载体
从全局域元素改为对应有限处的局部完成域元素，并保留 Scene1 中跨域完成映射的显式比较；
本次修订记录为 `Prologue-R3 → Prologue-R4`。这是载体修正，不新增数学假设。
S1.114 进一步移除 Prologue 中自由给定的 Tate 阶数，改为从完成域赋值派生；修订记录为
`Prologue-R4 → Prologue-R5`，不加入新的 3.12 假设。

边界移动必须同时记录两种负担：

- 晋升到 Prologue 可能减少 Scene1 的证明工作，但会增加对前置数学假设的信任负担；
- 从 Prologue 抽出并在 Scene1 实现可能增加当前证明工作，但会减少前置假设负担。

审计记录必须说明这两种负担的变化，不能只报告 Lean 文件变少或证明通过。

### 0.2 三层状态

动态边界使用三个状态层：

1. `Prologue/Core`：已接受的载体和无缺口的、来源明确的局部 `Prop` 契约。公开
   `Interfaces` 可以导入这一层。
2. `Prologue/Candidate`：为解释或尝试 3.12 而提出的候选声明。候选声明必须有来源
   和目标作用记录，但在审计决定前不得进入公开导入图，也不得成为 Scene1 的隐式
   参数。
3. `Scene1/Derived`：只服务于已形式化的 3.12、或由 Core 契约在 Scene1 中实际
   推出的命题。它必须以显式参数和完整 proof term 出现。

候选声明的状态只能是 `candidate`、`accepted`、`extracted`、`rejected` 或
`blocked`。`accepted` 才能晋升到 `Prologue/Core`；`extracted` 表示它已经从
Prologue 移出并由 Scene1 提供证明，不能仅表示换了文件名。

### 0.3 边界变更记录

每个变更使用唯一的 `change-id`，至少登记以下字段：

| 字段 | 要求 |
| --- | --- |
| `change-id`、旧/新 revision | 说明变更的唯一身份和边界前后版本 |
| `operation` | `promote`、`extract`、`split`、`derive` 或 `reject`；`derive` 表示用已有载体推导替代自由字段 |
| `declaration` | Lean 声明、文件和公开名称 |
| `target-role` | 它在 3.12 中承担的确切局部作用；未知时标为 `blocked` |
| `statement` | 完整类型或命题，不接受只写名称或自然语言摘要 |
| `source-ids`、`fidelity` | `SOURCE_LEDGER.md` 中的来源和忠实度说明 |
| `proof-status`、owner | `proved`、`conditional`、`open` 或 `blocked`，以及负责阶段 |
| `model-evidence` | 联合满足模型、违反模型或模型义务的精确位置 |
| `dependency-effect` | 导入图、证明参数和下游消费者的变化 |
| `circularity/minimality` | 说明它不等价于 3.12，并说明删除或弱化后的影响 |
| `burden-delta` | Scene1 证明负担和前置信任负担各自如何变化 |
| `decision`、时间和审查者 | `accepted`、`extracted`、`rejected` 或继续阻塞的理由 |

变更记录采用追加方式保存。旧 revision 的记录和来源位置不得被覆盖，以便答辩时
重放每一次边界移动。

### 0.4 晋升到 Prologue 的验收条件

只有同时满足以下条件，候选声明才可以从 `Prologue/Candidate` 晋升到公开
`Prologue/Core`：

- 它是独立、可复用的局部数学事实，而不是 3.12 或其等价不等式的改名；
- 载体字段进入 `Type`，性质进入 `Prop`，且所有字段有来源和数学解释；
- 有至少一个共同满足模型；若构造尚未完成，必须有单独命名的证明债务和 owner；
- 有违反模型、弱化模型或明确的模型义务，证明该声明不是恒真命题；
- Scene1 的计划证明确实消费其关键字段，而不是只把它作为装饰参数；
- `#print axioms`、导入审计和 `sorry` ledger 不显示隐藏的构造依赖；
- 晋升不会把 `Corollary312`、目标体积下界或最终主界塞进 Prologue；
- 变更记录完整说明它减少了哪一部分证明工作，以及增加了什么信任负担。

### 0.5 从 Prologue 抽取到 Scene1 的验收条件

下列声明应优先考虑抽取，而不是继续扩大 Prologue：

- 只对 3.12 的量词、归一化、符号或定量下界有意义；
- 已经包含 theta-volume 下界、主界或与 3.12 等价的结论；
- 其证明需要 Scene1 才有的 packet/hull 组合或目标特有的中间量；
- 在 Prologue 中存在会掩盖真正数学困难的宽泛假设。

抽取必须同时满足：声明移出公开 Prologue，Scene1 以显式参数或局部定义接收它，
并提供无 `sorry` 的证明或单独的、可审计的条件性桥接。抽取不能以删除字段、改名
或把同一命题放入另一个结构的方式完成。

### 0.6 直到 3.12 形式化前的冻结规则

在 `Corollary312` 的完整 Lean 类型、量词、归一化和来源位置确定前：

- 只允许对来源明确的载体和目标独立的结构性局部法律进行 Core 修订；
- 任何新的定量下界、`q` 项、全局体积结论或目标特有归一化都必须留在 Candidate；
- Candidate 不得被 `Interfaces`、Scene1 或 Scene2 导入；
- 不得以“证明变得容易”为理由晋升候选声明；
- 形式化目标确定后，必须先完成一次边界复审，再开始 `cor312_of_scene1_data`；
- 若现有 Prologue 合约不足以推出目标，应优先记录失败模型和最小增量，而不是直接
  把目标结论加入前置假设。

### 0.7 不可破坏的不变量

任何边界 revision 都必须保持以下不变量：

- Prologue 不包含 `Corollary312` 或其等价改写；
- Scene1/Scene2 不通过全局实例、隐藏常量或 `Prologue/Obligations` 获得输入；
- 所有未证明内容仍有唯一 source-id、证明 owner 和状态；
- 生产者输出必须有实际消费者，消费者字段必须可追溯到来源；
- 边界移动不改变已证明定理的声明，只能增加显式参数、证明或审计记录；
- Act2 仍只能在 Act1 的目标和桥接全部闭合后开始。
